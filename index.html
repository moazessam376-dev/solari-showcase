▤ 01 / THE EVIDENCE

The curve

I built solci around the question that actually changes a workflow: where does more CPU stop buying meaningful time?

THE SHORT VERSION
8x

2 vCPU = 8x cheaper than the GitHub run for this job (0.0012 vs 0.0100). GitHub figure is the private-repo rate, billed per minute rounded up, plus the $0.002/min platform fee.

That is the whole point of measuring the curve instead of guessing from a runner label.

◎
crosstalk's test job: 191 s at 1 vCPU, 197 s at 2 vCPU. Not CPU-bound. solci told me not to pay for more cores.

4 and 8 vCPU failed in the repo's own test suite, so those totals are not part of the recommendation.

◎ 02 / THE FRAME

Inspired by Blacksmith's [code]smith CI Tuning

I borrowed the question, then built the smallest honest instrument I could ship for the challenge.

01

[code]smith does

Turns run history into runner changes.

It reads previous runs, right-sizes runners, and proposes workflow changes. That is the product idea that sent me down this path.

02

solci does

Measures the job on real microVMs.

It runs one selected job at each requested size, records cost per run, and returns the findings behind the curve.

03

solci does not do

It is deliberately narrow.

No PR bot. No Docker or service jobs. One matrix cell. Linux only. The report says what it could not measure.

▸ 03 / THE RUNNER

How it works

The runner is a small sequence of decisions. Each one stays visible in the report.

01
gh

fetch workflow via gh

Read the workflow shape, job, runner label, history, and static findings.

02
mx

pick job and first matrix cell

Choose one job and the first literal value for each matrix axis.

03
vm

boot a microVM per size

1 s boot. vCPUs hot-plug in 1-15 s after boot, then the runner waits for cpu online.

04
sh

clone + shims

Clone into /work/repo. Shim setup-node, setup-python, uv, pnpm, and bun.

05
noh

run each step natively

Use nohup plus log polling around the 28 s exec cap for long steps.

06
out

curve, recommendation, findings

Write the evidence, then delete every sandbox when the run is done.

▤ 04 / STATIC CHECKS

Findings

Ten codes make the report useful before a run starts. Severity is a signal, not a verdict.

NO_CACHE_SETUPmedium

A supported setup action does not enable dependency caching.

UNPINNED_ACTIONlow

An action uses a mutable or missing ref.

NO_TIMEOUTlow

The job has no job-level timeout.

NO_CONCURRENCYlow

A pull-request workflow lacks a cancellation group.

FULL_CLONElow

Checkout requests the complete repository history.

SLOW_INSTALL_HINTinfo

pip install or non-lockfile npm install may be slower.

HIGH_FAILURE_RATEhigh

The history baseline has a failure rate above 20%.

BIG_RUNNERmedium

The job requests a large cores or vcpu runner.

SERVICES_UNSUPPORTEDinfo

The job uses Docker or service containers unavailable in Solari.

MATRIX_NOTEinfo

Only the first matrix cell was measured.

▸ 07 / GET STARTED

Install

Clone the repo, point it at your Solari and GitHub credentials, then ask one job for its curve.

git clone https://github.com/moazessam376-dev/solari-ci && cd solari-ci && uv pip install -e .
cp .env.example .env

Add SOLARI_API_KEY to .env.

export GITHUB_TOKEN=$(gh auth token)
solci doctor
solci run owner/repo --job test --cpu 1,2,4,8
